# ContextHub v2.3：AI 原生可审计知识中枢

> **文档类型：** 产品需求规格说明书（PRD）与系统架构设计基线  
> **版本：** v2.3（最终产品与架构基线）  
> **更新日期：** 2026-10-22  
> **文档状态：** 最终需求基线；生产实施须通过 Phase 0 技术与安全验证  
> **适用范围：** 个人知识 MVP、家庭知识协同、后续企业组织知识扩展  
> **设计原则：** 先可信、后自动；统一底座、分期交付；权限先于检索；故障可恢复、变更可追溯

## 0. 执行摘要与产品决策

### 0.1 产品定义

ContextHub 是一个以原始证据为基础、以可审阅的 Markdown 知识页为主要人类编辑界面、以 PostgreSQL 提供授权、任务状态、版本关系和可重建检索索引的 AI 原生知识中枢。它的核心价值不是简单“把文件放进向量库”，而是将分散资料转化为**有来源、有状态、有版本、有权限、有纠错路径**的可持续知识资产。

### 0.2 核心价值主张

1. **降低整理成本：** 用户通过文件投递或对话提交资料，系统自动完成解析、候选分类、知识编译和来源关联。
2. **提高知识可信度：** Wiki 页面必须保留原始证据引用；不确定的路由、识别结果和版本关系进入人工复核。
3. **减少检索错误：** 结合关键词、全文与向量检索，并在检索阶段按授权和当前有效版本过滤。
4. **持续演进而非一次性问答：** 支持补充、替代、纠错、审计和恢复，避免旧版本与新版本混杂。
5. **保护不同场景的边界：** 个人、家庭和企业数据虽共享技术底座，但授权范围、成员关系和内容规则独立管理。

### 0.3 项目准入条件

**最终决策：先交付个人知识闭环，再分阶段开放家庭与企业能力。** 本文定义产品和架构基线；Phase 0 安全与技术验证通过前，不开放家庭健康数据或企业机密资料的真实生产使用。

进入正式开发前的硬性准入项：

- 数据库授权和 RLS 覆盖范围经逐表盘点，并通过负向测试。
- 文件访问网关不接受客户端裸路径，路径、空间、类别和文档归属均经过验证。
- 文件系统与数据库采用可恢复的分阶段提交机制，不宣称跨系统原子事务。
- Markdown 与 PostgreSQL 的权威字段边界明确，双向同步具备冲突检测和恢复策略。
- 任务状态机、幂等规则、版本状态和回滚规则定义一致。
- MVP 的用户旅程、错误反馈、恢复与验收标准明确。

### 0.4 关键架构决策

| 决策 | 规则 |
|---|---|
| D-01：原始文件 | 原始字节不可变；系统生成的内容哈希用于去重与完整性验证。 |
| D-02：知识正文 | Wiki Markdown 是可读、可编辑的知识正文载体；普通正文可由用户在 Obsidian 中修改。 |
| D-03：系统元数据 | `doc_id`、空间归属、授权关系、版本指针、任务状态等由数据库与受控业务操作管理；Frontmatter 中对应字段属于受控投影，不能因手动改文本就直接改变权限或版本。 |
| D-04：检索索引 | 向量、全文和章节切片均为派生数据，可重建；不能作为权限事实源。 |
| D-05：不确定路由 | 禁止自动跨边界共享；进入隔离待确认流程。 |
| D-06：版本唯一性 | 每个逻辑文档系列通过数据库事务与唯一约束保证只有一个当前版本。补充文档作为独立关联实体管理。 |
| D-07：跨系统一致性 | 文件系统与 PostgreSQL 不存在单一原子事务；采用持久化状态、重试、补偿和恢复任务。 |
| D-08：授权模型 | 有效权限 = Token 范围 ∩ 当前成员权限 ∩ 空间继承规则 ∩ 文档类别规则；Token 本身不等同于内容授权。 |
| D-09：RLS 定位 | RLS 是纵深防御，不替代身份认证、授权服务、参数化查询、文件代理和安全测试。 |
| D-10：交付顺序 | 先个人知识闭环，再家庭健康，再企业组织树；数据模型可扩展不代表一期必须实现所有场景。 |
| D-11：模型接入 | 所有模型调用经统一 Model Adapter；客户端、n8n 节点和业务工具不得各自持有或直接使用供应商 API Key。 |
| D-12：模型职责 | LLM 负责理解、摘要、分类建议和答案组织；授权、版本提交、文件写入与任务状态由确定性服务端逻辑执行。 |
| D-13：首期模型范围 | 首期接入一个主 Chat/Vision 模型和一个 Embedding 模型；复杂任务可选升档模型；Reranker 按检索评测结果决定是否启用。 |

## 1. 背景、问题与产品目标

### 1.1 用户痛点

1. **整理成本高：** 下载目录、聊天记录、截图和项目资料长期堆积，用户需要手动重命名、分类和建立链接。
2. **检索缺少累积知识：** 单次 RAG 检索容易只返回碎片，无法稳定维护跨文档总结、事实台账和决策记录。
3. **版本混淆：** 新旧接口规范、排查结论或健康报告可能同时命中，导致回答基于过期信息。
4. **知识不可审阅：** 纯黑盒索引难以判断来源、纠错或确认 AI 是否误解原文。
5. **跨场景隐私风险：** 个人工作草稿、家庭合同、健康档案和企业知识不能因为方便检索就默认互通。

### 1.2 产品目标

**MVP 目标：** 在单个用户的 Personal Vault 中实现可重复、可恢复的“提交资料 → 安全预检 → 知识编译 → 可追溯检索 → 人工纠错 → 版本演进”闭环。

MVP 成功不以工具数量、向量库大小或自动化比例衡量，而以以下结果衡量：

- 用户不需要手工完成大部分基础分类和索引维护。
- 用户能够看见知识来自哪份原件、哪一页或哪一章节。
- 用户可以纠正分类、正文、提取指标和版本关系。
- 任务失败后可以定位、重试或撤销，不产生不可解释的半成品。
- 未经授权的数据不会通过检索、附件链接、缓存或日志旁路暴露。

### 1.3 非目标（MVP 明确不做）

- 不做多人同时编辑同一 Markdown 文件的实时协同。
- 不做企业级完整 IAM/SSO、组织审批流或合规认证。
- 不承诺任意格式、任意语言、任意扫描质量的 100% 正确解析。
- 不允许 AI 自动替代医疗专业判断；健康指标未经核验时必须显式标注。
- 不承诺文件系统与数据库跨系统事务原子性。
- 不把所有原始资料强制自动归档到正式知识库；归属不明时可以要求用户确认。
- 不在 MVP 中同时交付完整家庭健康与企业多级组织树。

## 2. 用户、场景与权限概念

### 2.1 用户与典型场景

| 用户 / 场景 | 核心任务 | 主要风险 | MVP 对应能力 |
|---|---|---|---|
| 个人知识管理者 | 整理项目文档、技术决策、个人资料和零散记录 | 整理成本高、旧版本误召回 | 入库、分类、编译、检索、版本和纠错 |
| 家庭资料管理者 | 共享保单、房产资料、家庭计划和长辈健康报告 | 成员误授权、敏感数据扩散 | Phase 2：家庭空间、邀请/撤权、健康指标复核 |
| 研发团队成员 | 检索 API 规范、ADR、排障复盘和代码符号关联知识 | 企业资料与私人资料串台 | Phase 3：组织空间、继承读取、受控发布 |
| 知识库维护者 | 处理待确认任务、版本冲突、同步错误与备份 | 隐性失败、索引和文件不一致 | 状态面板、审计、重试、恢复 |

### 2.2 基础概念必须分开

- **Space（空间）：** 权限、成员、存储根路径和知识域边界的容器。
- **Category（一级类别）：** 空间内的内容分类，例如 `01_Work`、`02_Life`、`03_Family`、`04_Health_Archive`。类别不是空间，也不能代替 ACL。
- **Membership（成员关系）：** 用户在指定空间内的角色和授权范围。
- **Profile（客户端访问配置）：** 为 IDE、家庭 Bot 或个人主力客户端限制可访问空间与类别的令牌配置。
- **Document（文档实体）：** 一个可授权、可追溯的知识对象。
- **Document Series（逻辑文档系列）：** 同一逻辑规范在不同版本之间的关系容器。
- **Ingestion Task（入库任务）：** 一次有状态、可幂等重放和可审计的操作。
- **Asset（原始资产）：** 原始文件字节或附件；经文档关系授权后方可被读取。

### 2.3 Space 分阶段模型

| 阶段 | 生效空间 | 用户体验 | 授权规则 |
|---|---|---|---|
| Phase 1：个人 MVP | 一个 Personal Vault | 无需用户手动选择空间；支持分类、检索和纠错 | 仍执行类别规则和敏感信息预检；单空间不等于所有资料都自动可用 |
| Phase 2：家庭协同 | Personal Vault + Family Hub | 家庭资料经过显式确认后复制/发布至家庭共享空间 | 家庭成员仅访问获授权的 Family Hub；不因是家庭成员而访问其他人的个人库 |
| Phase 3：企业组织 | 个人 + 家庭 + 企业组织树 | 支持组织继承读取和个人工作知识经审核后发布 | 企业公共空间、受限空间、个人类别分别校验；继承读取默认不继承写入 |

### 2.4 Profile 权限规则

1. **Work Profile：** 允许访问授权的企业空间，以及个人空间内明确允许的工作类别；不得访问个人生活、家庭、健康类别和家庭共享空间。
2. **Family Profile：** 仅允许访问显式授权的家庭共享空间及其允许的类别；不允许读取其他成员个人私有空间或企业空间。
3. **Omni Profile：** 仅用于个人可信设备；可以访问该用户当前成员授权范围内的所有个人类别，但仍不能自动获得所有家庭或企业空间权限。
4. **Profile 不绕过成员授权：** Token 中允许的空间必须与当下有效的成员关系取交集。成员移除后，即使旧 Token 尚未自然过期，也应在规定撤销时限内失效。
5. **只读和读写范围分开：** 读取权限不自动包含写入、重分类、版本替代、分享或删除权限。
6. **授权失败默认拒绝：** 缺失、过期、撤销、解析失败或范围不明确时，拒绝请求；不得自动回退至更宽泛的个人库。

### 2.5 总体架构与信任边界

└───────────────────────────────┬─────────────────────────────────────────┘

### 3.2 标准用户旅程

#### 旅程 A：普通文件入库

1. 用户通过 MCP 客户端提交文件，或将文件放入受控 Inbox。
2. 系统校验身份、令牌、目标空间写权限和文件基本有效性。
3. 系统生成幂等任务记录，计算 SHA-256，并将原始字节写入暂存区。
4. 系统提取正文、页码、章节、表格及可识别图片；失败时保留错误原因。
5. 路由规则先判断硬条件，再用 LLM 提出候选类别和理由。
6. 明确且符合规则的文档进入编译；模糊或跨边界的文档进入 `NEEDS_REVIEW`。
7. 编译出 Markdown 草稿，写入来源信息、标题、摘要和必要的 Frontmatter。
8. 完成可恢复提交流程，写入检索索引，并返回结构化回执。
9. 用户可以检索、打开来源、纠错或撤销任务。

#### 旅程 B：归属不明或跨场景内容

1. 系统不把内容自动塞入某个正式空间。
2. 任务进入隔离队列，并保存候选空间、触发规则、模型建议和原因。
3. 用户可选择批准某个候选、重新分类、拆分文档或取消任务。
4. 执行前重新验证目标空间权限；任务批准不等于权限自动提升。
5. 所有决定和变更写入审计记录。

#### 旅程 C：Obsidian 修改正文

1. 文件监听器读取变更文件，忽略编辑器临时文件及系统生成文件。
2. 校验空间路径、Frontmatter schema 和文件对应的 `doc_id`。
3. 对受保护系统字段的修改拒绝直接应用；必要时生成冲突报告。
4. 使用内容版本/哈希判断是否基于最新版本修改；存在并发冲突时生成待解决副本，不静默覆盖。
5. 同步正文和可编辑元数据，重新生成切片和检索索引。
6. 记录操作者、修改时间、前后版本和同步结果。

## 4. 入库、路由与任务状态机

### 4.1 路由原则

路由是“提出候选并执行规则”，不是让 LLM 决定权限。

优先级从高到低：

1. **显式目标：** 用户明确给出 `target_space_id`，系统必须先验证其写权限与内容合规性。目标未授权时直接拒绝，不允许自动换到其他空间。
2. **受控投递路径：** 用户通过已挂载并授权的空间别名投递。路径只能提示目标，仍需服务端校验授权。
3. **确定性规则：** 类别白名单、已知业务标识、代码符号或已确认的文档系列命中。
4. **语义候选：** LLM 对内容进行类别建议，输出候选、理由和不确定因素。
5. **人工确认：** 信号冲突、多意图混合、涉及敏感资料或目标不明确时进入待确认。

以下情况不得自动提交正式空间：

- 目标空间不在有效写权限内。
- 文档同时混合个人隐私和企业正式资料，且无法可靠拆分。
- 文件包含高风险敏感信息，但当前 Profile 或目标空间不允许处理。
- 文档解析失败、来源不明或内容/元数据校验失败。
- 版本替代目标不明确，或与已有系列发生冲突。

敏感信息检测只能作为风险预检，不应被当作绝对正确的内容分类器。漏检不能成为越权访问的理由，真正的保护仍由空间授权和类别授权执行。

### 4.2 任务状态定义

| 状态 | 含义 | 是否对正常检索可见 | 可执行动作 |
|---|---|---|---|
| `RECEIVED` | 已登记请求与幂等键 | 否 | 预检 |
| `PRECHECKING` | 正在检查身份、目标和文件 | 否 | 进入路由或失败 |
| `ROUTING` | 规则与模型正在形成路由决定 | 否 | 编译或待确认 |
| `NEEDS_REVIEW` | 等待用户确认目标、提取或版本关系 | 否 | 批准、重新分类、拆分、取消 |
| `STAGED` | 临时文件和编译产物已准备 | 否 | 开始发布提交 |
| `COMMITTING` | 正在执行可恢复发布流程 | 否 | 完成提交或由恢复任务接管 |
| `COMMITTED` | 文件、业务元数据和可用索引均达到提交条件 | 是 | 检索、纠错、版本演进 |
| `FAILED_RETRYABLE` | 临时故障，可重试 | 否 | 自动或人工重试 |
| `FAILED_FINAL` | 无法自动恢复或输入不满足规则 | 否 | 修正输入、重新提交或取消 |
| `CANCELLED` | 用户取消且未完成提交 | 否 | 保留审计，按保留策略清理暂存 |
| `REVERTED` | 相关操作已被有效撤销 | 取决于当前文档状态 | 查审计、重新执行受控操作 |

### 4.3 合法状态迁移

```text
RECEIVED -> PRECHECKING
PRECHECKING -> ROUTING | NEEDS_REVIEW | FAILED_RETRYABLE | FAILED_FINAL | CANCELLED
ROUTING -> STAGED | NEEDS_REVIEW | FAILED_RETRYABLE | FAILED_FINAL | CANCELLED
NEEDS_REVIEW -> ROUTING | STAGED | CANCELLED
STAGED -> COMMITTING | FAILED_RETRYABLE | CANCELLED
COMMITTING -> COMMITTED | FAILED_RETRYABLE
FAILED_RETRYABLE -> 原失败阶段继续执行 | FAILED_FINAL | CANCELLED
COMMITTED -> REVERTED（仅指已撤销的业务操作，不删除历史审计）
```

非法状态迁移必须被服务端拒绝；状态变更、操作者、时间、重试次数与错误编码均需持久化。`COMMITTED` 只能由服务端在全部提交条件满足后写入，不能由模型或客户端声明。

### 4.4 幂等规则

**文件任务幂等键：** 基于 `user_id + canonical_file_hash + explicit_target_or_route_context + operation_type` 生成稳定键；不使用原始文件名作为唯一依据。若用户明确要求重新处理同一原件，应通过新的操作类型或显式 `reprocess_generation` 区分。

**内容去重：** 文件 SHA-256 用于原始字节完整性检查与资产去重；不自动代表两份文档的业务语义相同。

**台账追加幂等：** 每条新增台账记录有独立 `event_id`，同一任务重放不得重复追加。

**并发领取：** Worker 领取任务必须通过数据库原子更新、租约或等效机制防止多个 Worker 同时推进同一任务。租约超时后可被恢复流程接管。

**幂等不等于跳过全部检查：** 即使请求已存在，也要确认当前调用者有权读取结果任务和原文档，不能因命中幂等键泄露其他用户的任务状态。

### 4.5 文件与数据库的可恢复提交

文件系统与数据库之间没有统一原子事务。系统采用以下持久化 Saga 流程：

1. **接收与暂存：** 将原件写入受控暂存目录，完成哈希与基本校验；暂存目录不得被正常检索访问。
2. **准备数据库记录：** 在一个 PostgreSQL 事务内创建/锁定文档系列、待发布文档、任务状态和 Outbox 事件；文档处于 `PENDING_PUBLISH`，不可被正常检索。
3. **发布文件：** 将已校验的临时文件原子移动至正式文件位置。临时与正式目录必须满足实际部署的原子重命名条件；否则实现复制、校验和完成标记流程。
4. **最终提交：** 在第二个 PostgreSQL 事务中，将文档置为可用状态，更新当前版本指针、切片状态和任务状态；只有达到可检索条件后任务才能成为 `COMMITTED`。
5. **异常恢复：** 恢复 Worker 检查任务记录、临时文件、最终文件、校验和及 Outbox 状态。能继续则继续；无法自动判定时进入人工复核，不静默删除数据。
6. **补偿处理：** 对已经发布但不能完成业务提交的文件，根据任务审计决定重试、转隔离或清理；清理必须校验其未被其他已提交文档引用。

不把“事务回滚”用作文件系统与数据库整体一致性的承诺；产品承诺是**可检测、可重试、可恢复、可审计**。

## 5. 知识模型、版本与内容治理

### 5.1 空间目录约定

```text
ContextHub_Data/
├── 00_Inbox/                         # 受控收件入口，不是正式知识空间
├── 01_Processing/                    # 暂存与处理中间产物，不可由正常检索访问
├── 02_Vault/
│   └── spaces/<space_id>/
│       ├── SPACE_SCHEMA.md
│       ├── index.md
│       ├── log.md
│       ├── _dashboard_控制台.md
│       ├── raw/                      # 原始证据/资产的受控引用或只读副本
│       ├── wiki/                     # 正式知识 Markdown
│       └── _archive/                 # 可选的人类可读归档视图，不作为唯一历史存储
├── 99_Review_Required/               # 待确认队列的受控暂存视图
└── ops/                              # 任务、日志、备份清单等运营资产
```

实际原始资产存储可以按 SHA-256 内容寻址，原始文件名保存为元数据而不是直接拼接为磁盘路径。对用户展示的文件名应进行安全转义。`99_Review_Required` 不应因文件落在该目录就被默认授权给所有空间成员。

### 5.2 权威数据源边界

| 数据 | 权威来源 | 可否人工编辑 | 说明 |
|---|---|---|---|
| 原始文件字节 | 不可变原始资产存储 | 否 | 更正应新增版本或新增文件，不覆写原件 |
| Wiki 正文 | Markdown 文件 | 是 | 用户修改会触发校验、版本记录及索引重建 |
| 系统文档 ID、空间归属、授权、版本指针、状态 | PostgreSQL 及受控命令 | 不允许通过随意改 Frontmatter 直接修改 | Frontmatter 中的对应值为校验/展示投影 |
| 用户可编辑元数据，如标题、摘要、部分标签 | 依据 schema 的 Markdown/数据库同步契约 | 是 | 明确双向同步规则及冲突处理 |
| 任务状态和审计 | PostgreSQL | 否 | 只可通过受控业务命令改变 |
| 向量、全文索引、章节切片 | 可重建索引 | 否 | 从当前有效正文重新生成，带索引版本信息 |
| 健康指标 | 结构化指标记录与原始报告关联 | 受控编辑 | AI 提取值、人工核验值和更正历史应区分 |

### 5.3 文档身份与版本模型

建议把**逻辑文档系列**与**具体版本**分开建模，避免 `is_latest`、`doc_status`、Frontmatter 状态和文件路径相互竞争。

- `document_series`：包含 `series_id`、`space_id`、`version_key`、`current_doc_id`、修订号和时间戳；唯一约束为 `(space_id, version_key)`。
- `documents`：每条记录代表一个具体版本，保存 `doc_id`、`series_id`、`file_hash`、原始资产引用、Wiki 相对路径、状态、来源、创建人和时间。
- 当前版本由 `document_series.current_doc_id` 作为权威指针；切换时锁定系列行并在单个数据库事务中完成。
- 若采用 `is_current` 辅助字段，必须与 `current_doc_id` 保持一致并用约束/触发器或单一写入路径控制，避免双重事实源。
- 主版本系列使用稳定的 `version_key`。补充页是独立关联实体，不能与主版本争用同一个当前版本唯一键。
- 旧版本保留历史和审计，不因被替代就必须物理移动文件。检索默认只取当前有效版本，用户明确查询历史时才提供旧版本。

### 5.4 版本业务规则

| 场景 | 规则 |
|---|---|
| 完全重复上传 | 原始资产哈希相同且目标空间、文档身份语义一致时返回已有结果；不可仅凭哈希推断它们在所有业务场景中均为同一文档 |
| 新建文档 | 创建新 `doc_id`；若属于有版本控制要求的主题，应确定 `version_key` 并建立系列关系 |
| 全量替代 `REPLACEMENT` | 必须先确认目标系列；锁定系列行；创建新版本；在同一 DB 事务中更新当前版本指针与版本状态 |
| 增量补充 `SUPPLEMENT` | 创建独立补充文档，通过 `parent_doc_id` 或关系表关联主文档；主文档正文不被自动重写为包含不可审计的复制内容 |
| 版本回滚 | 按 `series_id` 锁定系列，验证操作者权限和预期当前版本，再切换当前指针并重建/切换索引；保留回滚事件和前后差异 |
| 版本冲突 | 两个任务同时替代同一系列时采用锁与乐观版本检查；后提交任务必须重新评估，不能覆盖已变化的当前版本 |
| 删除与撤销 | 默认软删除/撤销可追踪；物理清理需经过引用检查、保留期限和授权校验 |

### 5.5 Markdown Frontmatter 契约

示例（示意字段，最终 schema 由实现阶段固定）：

```yaml
---
doc_id: "<server-generated-uuid>"
space_id: "<server-controlled-space-id>"
series_id: "<server-generated-series-id>"
version_key: "uc_api_wechat_pay_callback"
version_label: "v2.1"
source_asset_ids:
  - "<asset-id>"
source_task_id: "<task-id>"
content_revision: 7
review_status: "APPROVED"
tags:
  - payment
  - callback
---
```

规则：

- `doc_id`、`space_id`、`series_id`、当前版本关系和任务状态由系统控制；用户直接修改时应被拒绝或转为待确认。
- `content_revision` 由同步服务维护，用于并发检测。
- 可编辑标签、摘要等字段必须在 schema 中明确，不接受任意未知字段静默写入数据库。
- Frontmatter 校验失败时保留用户文件，生成同步错误，不得自动覆盖用户内容。

### 5.6 来源与引用

每个正式 Wiki 页面必须关联一个或多个来源记录。来源记录至少包含：

- 原始资产 ID 和 SHA-256；
- 原始文件名称和格式；
- 页码、章节标题、段落或表格位置（若可提取）；
- 入库任务 ID、处理时间、解析器/模型版本；
- 人工修正和复核状态（如适用）。

检索回答必须区分“引用片段”和“AI 总结”。系统应验证引用片段确实存在于对应来源或其可追溯转换结果中；不能仅因生成了页码字段就认为溯源成立。

## 6. 模型接入、检索与回答质量

### 6.1 检索流程

1. 验证 Token、当前成员关系和 Profile 范围。
2. 解析授权后的可读空间、类别和文档集合。
3. 执行全文/关键词检索与向量检索；代码场景可加入符号索引。
4. 在排名融合前后均保证未授权数据不会进入候选上下文。
5. 过滤非当前有效版本；只有用户明确请求历史资料时才允许检索历史版本。
6. 对命中的主文档按规则关联有效补充文档；补充文档同样必须通过授权和状态过滤。
7. 返回引用文本、文档标题、版本、章节/页码、来源链接及必要的核验标记。
8. 若证据不足或结果冲突，明确告知资料不足，不以无来源推断补齐事实。

### 6.2 排序原则

- 首先是授权与可见性，而不是相关性分数。
- 默认优先当前有效版本。
- 在授权范围内，可考虑直属空间、明确继承的公共空间、用户个人笔记的优先级；此排序不能突破权限边界。
- `index.md` 可作为空间导航与候选发现入口，不应成为唯一检索来源或绕过文档 ACL 的入口。
- BM25/全文和向量检索的融合算法作为可替换实现，通过固定问题集评估，不在 PRD 阶段锁定未经验证的权重。

### 6.3 检索质量指标

| 指标 | 定义 | 初始目标/方法 |
|---|---|---|
| Recall@5 | 相关资料是否进入前 5 个结果 | 用人工标注问题集建立基线后设定目标 |
| 引用存在率 | 回答中的引用是否存在于来源 | 正式答复引用应 100% 可定位 |
| 引用正确率 | 引用是否真正支持对应陈述 | MVP 目标 ≥ 95%，样本和评审规则需预先固定 |
| 过期版本误召回率 | 未请求历史时，旧版本进入有效结果的比例 | 目标为 0；通过查询级过滤和回归测试保障 |
| 无证据回答率 | 在证据不足时仍给出明确断言的比例 | 建立基线并持续下降；高风险场景采用保守策略 |
| 权限越界召回数 | 不应可见内容进入结果或上下文的次数 | 目标为 0，并以自动化负向测试验证 |


### 6.4 大模型接入与最终选型

#### 6.4.1 最终架构决策

ContextHub 采用**统一 Model Adapter + 按任务路由 + 独立 Embedding**的模型接入方式。第一期不建设模型平台，不为每条 n8n 工作流分别维护供应商连接，也不要求在 NAS 上运行大型推理模型。

- **首选供应商：** 阿里云百炼 Model Studio，作为 Phase 0/1 的首个模型接入渠道；使用与部署地域匹配的官方 API Endpoint 和 API Key。
- **主模型：** `qwen3.8-flash`，承担常规文本理解、分类建议、摘要、Wiki 编译和检索答案组织；在服务地域和对应接口确认支持视觉输入后，也用于图片/扫描件的补充理解。
- **复杂任务升档模型：** `qwen3.8-max`，仅用于跨文档冲突、复杂综合或主模型处理失败且需要更强推理的任务；不是默认每次调用。
- **Embedding 模型：** `text-embedding-v4`，初始向量维度固定为 `1024`，与当前 `vector(1024)` 设计保持一致。Phase 0 应在目标地域验证模型可用性、实际返回维度、中文/英文/代码检索效果与成本。
- **OCR/文档解析：** 优先采用本地解析器与 OCR 处理可提取的文本；对于复杂表格、低质量扫描件和图像内容，再调用支持视觉输入的模型。首期不强制引入单独的 OCR 模型服务。
- **Reranker：** Phase 1 默认不启用。固定问题集证明混合检索排序仍有明显不足后，再选择目标地域实际支持的重排模型并评估成本与收益。

上述模型名称是首期的推荐默认配置，不构成对任何地域、账户、模型套餐或接口能力的无条件保证。Phase 0 必须从目标账户验证模型清单、Endpoint、输入格式、结构化输出能力、限流和计费规则；不可用时，通过配置替换为同能力且已验证的模型，不改动业务状态机。

#### 6.4.2 模型与任务映射

| 任务 | 默认方案 | 升级/降级规则 | 强制约束 |
|---|---|---|---|
| 内容分类与路由建议 | `qwen3.8-flash` | 结果不满足结构化 schema、规则冲突或任务复杂时，可升档一次；仍不确定则 `NEEDS_REVIEW` | 模型不得签发权限、扩大目标空间或自行批准共享 |
| Wiki 编译与摘要 | `qwen3.8-flash` | 长文或跨文档综合可按策略升档至 `qwen3.8-max` | 正式正文必须保留来源关系；无证据内容不得伪装为原文事实 |
| 检索问答 | 先完成授权后的混合检索，再由 `qwen3.8-flash` 组织答案 | 证据冲突或复杂问题可升档；证据不足时应明确说明 | 未授权或失效版本内容不能进入模型上下文 |
| 图片/扫描件理解 | 本地解析/OCR 优先；必要时使用已验证的视觉模型 | 若不可读或关键字段存疑，进入人工复核 | 不得把模型置信描述当作真实性证明 |
| 向量生成 | `text-embedding-v4`，1024 维 | 替换模型时新旧索引分区或全量重建 | 不同模型/版本向量不能混在同一索引空间中 |
| 检索结果重排 | 首期关闭 | 评测证明有收益后再启用目标地域支持的模型 | 不得突破授权过滤或当前版本过滤 |
| 健康报告指标提取 | Phase 2：解析/OCR + 已审核的视觉/文本模型 | 模糊、缺单位、参考范围不明确时进入 `NEEDS_CHECK` | 外部服务的数据处理与地域条件须先获准；未经核验不可标记为事实 |

#### 6.4.3 接入位置与调用链

```text
MCP Client / Obsidian
        │
        ▼
FastMCP Gateway ─── 身份认证、权限计算、参数校验
        │
        ├── 实时问答：授权过滤 → PostgreSQL 混合检索 → Model Adapter → 答案与引用
        │
        └── 异步入库：Worker / n8n → 解析与预检 → Model Adapter → Wiki 编译/分类建议
                                             │
                                             ├── Chat/Vision Client → Model Studio
                                             └── Embedding Client  → Embedding API
```

实施边界：

1. FastMCP Gateway 和异步 Worker 调用同一套 Model Adapter 接口；n8n 负责编排，不应在每个节点中重复硬编码供应商地址或 API Key。
2. 客户端不得直接持有云模型凭证，也不得绕开 ContextHub 直接请求内部知识库的模型上下文。
3. Model Adapter 负责供应商协议适配、请求/响应标准化、超时、限流、有限重试、模型配置、用量计量和错误归类。
4. 模型输出视为不可信数据。分类和结构化提取结果必须经过 JSON Schema/Pydantic 校验及业务规则校验；任何数据库写入、文件发布、版本切换、授权变化都必须由受控服务端代码执行。
5. 对外部 API 的临时故障，按策略重试后转为 `FAILED_RETRYABLE`；不可将模型调用失败解释为任务成功，也不可因失败自动扩大访问范围或改投更宽泛空间。

#### 6.4.4 统一适配层接口

应用层至少提供以下接口，具体语言实现可在 Phase 0 决定：

- `ChatModelClient.generate()`：接收任务类型、受控上下文、输出 schema 和模型策略，返回经过 schema 校验的结构化输出及模型调用元数据。
- `EmbeddingClient.embed_documents()`：为正文切片生成向量。
- `EmbeddingClient.embed_query()`：为检索问题生成查询向量；查询和文档向量使用同一模型/版本与兼容的编码策略。
- `RerankerClient.rerank()`：可选接口，第一期可不实现或默认关闭。

建议通过配置项管理 `provider`、`region`、`model_id`、`api_endpoint`、`request_timeout`、`max_retries`、`max_output_tokens`、`prompt_version`、`output_schema_version`、`embedding_dimension` 与 `index_version`。API Key 通过环境变量或 Docker Secrets 注入；禁止提交到 Git、Markdown、配置样例或日志中。

#### 6.4.5 数据隐私与模型调用边界

- 云模型处理意味着请求中的文本、图像或文档片段会被发送到所选供应商。数据库/RLS 保护并不意味着外发的数据仍完全留在本地。
- 在模型调用前先完成身份、目标空间和数据处理策略检查。只发送任务所必需的内容，优先使用相关切片而非整库上下文。
- 对身份证件、合同、家庭健康资料、企业机密等敏感类别，必须依据空间策略决定是否允许外部模型处理；未授权时应拦截、脱敏、采用已批准的本地方案或进入人工确认。
- Phase 2 健康模块上线前，需要确认供应商数据使用条款、处理地域、日志/保留策略和适用的组织合规要求。没有完成确认前，不将真实健康档案发送给外部模型。
- 日志默认仅记录 `task_id`、`doc_id`、Provider、模型 ID、提示词版本、耗时、Token 用量、费用估算和错误码；不默认记录原始提示词、原件内容、完整模型响应或健康指标。
- 供应商 API Key、Token 和凭证不写入文档，不随 MCP 任务回执返回，不以模型提示词方式暴露。

#### 6.4.6 Embedding 版本管理

`embedding_provider`、`embedding_model`、`embedding_dimension` 和 `embedding_version` 属于索引配置，必须与每个索引批次关联。模型升级时不得直接把新向量写入旧模型索引。迁移流程为：建立新索引版本 → 批量重算 → 对数量和检索质量做校验 → 切换当前索引版本 → 在回滚窗口结束后清理旧索引。

首期维度固定为 1024。若实际接入的模型不支持 1024 维，必须在迁移脚本、数据库向量列、索引及验收测试中一并变更，不能仅修改应用配置。

#### 6.4.7 模型调用质量与成本控制

- 对不同任务类型使用固定的系统提示词/模板版本、明确的输出 schema 和可复现测试集。
- 不以模型自报的 `confidence` 直接批准高风险路由；路由依据包括确定性规则、历史系列匹配、允许范围和冲突信号。证据不足时人工确认。
- 设置单任务输入/输出上限、最大重试次数、调用超时和日/月预算告警。大批量向量化优先使用批处理能力，但须在目标地域验证限额与计费。
- 通过 Golden QA Set 衡量分类准确率、引用支持率、过期版本误召回、人工复核率和单位文档处理成本；模型升级后重跑回归测试。
- 缓存只能存储在与原文同等或更严格的访问控制范围内；缓存键必须包含授权范围、模型/提示词版本和数据版本，避免跨用户或跨空间复用敏感结果。

## 7. 安全与权限架构

### 7.1 安全边界

安全目标不是宣称“绝对零信任”，而是实现明确、可验证的多层保护：

1. **身份层：** 高熵随机 Token；数据库只存 Token 哈希；Token 有明确过期时间、撤销状态和签发记录。
2. **授权层：** 服务端计算有效空间、类别及读写范围；每次请求均执行授权检查。缓存必须有可验证的失效策略。
3. **数据库层：** 最小权限数据库角色、必要表的 RLS、明确的命令级策略和数据库约束。
4. **文件层：** 客户端只传 `doc_id` 或 `asset_id`；后端从受控记录解析文件位置并校验路径、空间、类别和文档关联。
5. **工作流层：** n8n 只处理必要字段；凭证按工作流和用途隔离；失败和重试不能扩大权限。
6. **运营层：** 审计、密钥管理、备份、恢复演练、日志脱敏和异常告警。

### 7.2 权限计算

```text
有效读取范围 = Token 允许的空间/类别
             ∩ 当前有效 Membership 与空间继承规则
             ∩ 文档/附件的空间与类别规则

有效写入范围 = Token 写入范围
             ∩ 当前 Membership 角色（WRITER/ADMIN）
             ∩ 空间与类别写入规则
             ∩ 当前业务操作允许的变更范围
```

任何一个授权条件不满足或无法计算，都拒绝访问。空间树继承规则必须明确：默认只继承指定的公共读取权限；不默认继承写入权限，也不默认让家庭空间向其他空间继承。

### 7.3 PostgreSQL / RLS 实施要求

- 使用独立迁移角色创建表和策略，业务连接角色不得为 superuser、表所有者或 `BYPASSRLS` 角色。
- 对确需行级隔离的所有业务表启用 RLS，并按需要使用 `FORCE ROW LEVEL SECURITY`；逐表登记覆盖范围和例外。
- 业务账号只获得精确到表、视图或函数的权限。禁止无差别地对所有表授予 CRUD。
- 对 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 明确建立命令级策略；`UPDATE` 必须校验旧行可见/可改范围及新行写入后的空间与类别。
- 不使用一个 `FOR ALL` 策略声称已经实现严格读写分离。策略组合必须按 PostgreSQL 的 permissive/restrictive 规则进行整体审查与测试。
- 缺失、空值或无效的授权上下文必须拒绝访问；不允许将未配置的范围解释成无限授权。
- 对 `SECURITY DEFINER` 函数设置安全的 `search_path`，使用完全限定对象名，收紧 `EXECUTE` 授权，并审计函数所有者权限。
- **重要限制：** 由应用设置的自定义 PostgreSQL 参数（如 `app.allowed_read_spaces`）本身不是抵御任意 SQL 执行的独立身份凭证。只有在数据库仅由受控服务访问、查询参数化、客户端不能直连、应用注入上下文受到严格约束的前提下，才可将此机制作为纵深防御。若威胁模型包含不可信主体能够以业务账号执行任意 SQL，必须采用更强的身份绑定/执行接口设计，不能依赖 GUC 自证权限。
- 对缓存授权结果设定最大 TTL，并为 Token 撤销、成员移除提供主动失效机制；“即时生效”须以实测 SLO 表达，不用未经测试的绝对承诺。
- 为避免 UPDATE 因 RLS 同时要求既有行可见而失败，默认将同一行的有效写权限纳入该行的可读权限；不支持隐式的“可修改但完全不可见”模式。如未来需要 write-only 操作，应通过独立、严格限制的业务函数实现。

#### 7.3.1 命令级策略实施检查表

| 操作 | 既有行检查 | 新行检查 | 关键要求 |
|---|---|---|---|
| `SELECT` | 读取范围与类别规则 | 不适用 | 未设置或为空的上下文必须拒绝 |
| `INSERT` | 不适用 | 写入空间与类别规则 | 不允许客户端自行设置授权上下文；新 `space_id` 必须属于当前写入范围 |
| `UPDATE` | 旧行必须在有效可见/可写范围 | 新行仍必须在有效写入范围 | 阻止通过更新 `space_id`、`category` 或归属字段越权移动记录 |
| `DELETE` | 被删除行必须在有效写入范围 | 不适用 | 不允许仅凭知道 ID 删除记录 |

以下仅为**策略审查示意**，不是完整迁移脚本；实际策略还必须结合 `category`、实体关系、角色权限和所有多租户表验证：

```sql
-- 受保护表必须分别开启并强制 RLS；迁移角色和在线业务角色分离。
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE ROW LEVEL SECURITY;

-- 查询范围由受控网关按每次请求计算；空上下文不授权。
CREATE POLICY docs_select_policy ON documents
  FOR SELECT TO contexthub_gateway
  USING (
    NULLIF(current_setting('app.allowed_read_spaces', true), '') IS NOT NULL
    AND space_id = ANY(
      string_to_array(current_setting('app.allowed_read_spaces', true), ',')
    )
  );

CREATE POLICY docs_insert_policy ON documents
  FOR INSERT TO contexthub_gateway
  WITH CHECK (
    NULLIF(current_setting('app.allowed_write_spaces', true), '') IS NOT NULL
    AND space_id = ANY(
      string_to_array(current_setting('app.allowed_write_spaces', true), ',')
    )
  );

CREATE POLICY docs_update_policy ON documents
  FOR UPDATE TO contexthub_gateway
  USING (
    NULLIF(current_setting('app.allowed_write_spaces', true), '') IS NOT NULL
    AND space_id = ANY(
      string_to_array(current_setting('app.allowed_write_spaces', true), ',')
    )
  )
  WITH CHECK (
    NULLIF(current_setting('app.allowed_write_spaces', true), '') IS NOT NULL
    AND space_id = ANY(
      string_to_array(current_setting('app.allowed_write_spaces', true), ',')
    )
  );

CREATE POLICY docs_delete_policy ON documents
  FOR DELETE TO contexthub_gateway
  USING (
    NULLIF(current_setting('app.allowed_write_spaces', true), '') IS NOT NULL
    AND space_id = ANY(
      string_to_array(current_setting('app.allowed_write_spaces', true), ',')
    )
  );
```

实施注意：以上策略只展示空间维度。真实系统还必须执行类别白名单、行关系及目标资产关联校验；其他业务表也要建立相应策略。`current_setting` 等应用上下文变量并非独立身份凭证，网关必须仅使用参数化 SQL、禁止客户端直连，并避免任何不可信请求进入任意 SQL 执行路径。上线前必须在真实 PostgreSQL 版本与实际角色配置中执行测试。

### 7.4 数据库账号职责

| 角色 | 职责 | 禁止事项 |
|---|---|---|
| `contexthub_migrator` | 迁移、建表、索引、策略变更 | 不用于在线业务请求 |
| `contexthub_gateway` | 通过受控 SQL/函数访问授权数据 | 不具备 superuser、`BYPASSRLS`，不拥有受保护表 |
| `contexthub_auth_reader`（可选） | 验证 Token、读取必要授权元数据 | 不直接读取原始正文或任意业务内容 |
| `contexthub_worker` | 由服务端控制的工作流执行必要读写 | 不使用高权限账号绕过业务授权 |
| `backup_operator` | 按备份策略执行备份/恢复 | 凭证独立管理，不放入普通工作流变量 |

最终账号拆分方式由 Phase 0 验证，但在线网关禁止使用数据库超级用户和迁移账号。

### 7.5 文件访问安全

- MCP 参数仅允许 `doc_id`、`asset_id`、经枚举校验的 `asset_type` 等受控标识，不接受客户端给出的服务器路径。
- 服务端查询授权文档记录后，按内部映射解析相对路径；不得把 Frontmatter 中的任意路径直接拼入文件路径。
- 标准化路径后检查它严格位于预期根目录内，并再次校验文档所属空间和资产关联；单纯字符串前缀比较不合格。
- 明确防护符号链接、路径穿越、相邻目录同前缀、文件替换竞态和非预期硬链接等风险。
- 文件流、Base64 内容、临时 URL 与缓存都必须继承同等授权；拒绝后不得留下可复用的公开链接。
- 对附件大小、MIME 类型、压缩包展开、解压路径和恶意文件扫描设定限制。

### 7.6 Token 和授权变更

- Token 必须有签发者、创建时间、过期时间、Profile、作用范围、撤销时间和审计关联。
- 令牌不在日志、提示词、任务回执或错误信息中输出。
- 撤销 Token 和移除 Membership 时，授权缓存需主动失效；目标为撤销在约定 SLO 内生效（Phase 0 需要测试确认，例如 5 秒以内），未通过前不得宣传为“即时”。
- 任何空间迁移、共享、晋升或重新分类都必须以执行时权限为准，不沿用任务创建时可能已经失效的授权结论。

### 7.7 日志与数据保留

- 日志记录 task ID、doc ID、操作类型、结果、耗时与错误码；不默认记录完整原文、Token、健康指标或敏感字段。
- 原件、Wiki、任务、审计、向量索引和备份分别定义保留与删除策略。
- 用户发起删除时，应说明正式存储、派生索引、缓存、Git 历史及备份中删除的不同时间边界。
- Git 适合用于受控知识文件的版本审计，但不自动等于敏感数据的安全备份；涉及家庭健康或企业机密时需要评估仓库加密、远程仓库、历史清理及访问范围。

## 8. 核心数据模型（逻辑设计）

本节是逻辑模型和实现约束，不等同于可直接运行的完整迁移脚本。具体列、外键、权限和索引需在 Phase 0 形成可执行版本并经过安全审查。

| 实体 | 主要字段/关系 | 关键约束 |
|---|---|---|
| `users` | `user_id`、显示名、创建时间、状态 | 用户状态不能仅通过删除所有关联数据进行隐式处理 |
| `spaces` | `space_id`、类型、父空间、路径、一级类别 schema | 空间类型不能依靠 ID 字符串前缀判断；路径需唯一且受控 |
| `space_memberships` | 用户、空间、角色、继承策略、撤销时间 | 成员关系唯一；角色与继承行为定义明确 |
| `access_tokens` | Token 哈希、Profile、允许范围、过期与撤销时间 | Token 原文不入库；必须过期；撤销有审计 |
| `assets` | `asset_id`、SHA-256、内容存储位置、MIME、大小、创建时间 | 原始内容不可变；磁盘路径由服务端生成；去重与访问授权分开 |
| `documents` | `doc_id`、空间、类别、Wiki 路径、状态、来源关系 | 文档路径不允许跨空间；系统字段只由受控服务修改 |
| `document_series` | `series_id`、空间、`version_key`、`current_doc_id` | `(space_id, version_key)` 唯一；当前指针经事务修改 |
| `document_relations` | 来源文档、目标文档、关系类型 | 用于 SUPPLEMENT、派生、晋升、引用等关系；关系读取同样需授权 |
| `document_chunks` | 文档、版本、章节、页码、正文、embedding | 只能用于其所属文档授权范围；版本失效后不能被默认召回 |
| `ingestion_tasks` | 任务 ID、幂等键、用户、目标、状态、重试、错误和审计 | 幂等键唯一；合法状态迁移；任务结果读取需授权 |
| `outbox_events` | 事件 ID、类型、载荷、投递状态和重试次数 | 支撑可恢复的文件发布、索引更新和通知 |
| `health_metrics` | 来源文档、人员、指标、数值/文本、单位、参考范围、核验状态 | 指标必须关联来源；原始提取与人工核验区分；访问受健康资料授权控制 |
| `audit_events` | 操作人、动作、对象、前后状态摘要、时间、请求 ID | 仅追加或受控修正；不能由普通知识正文编辑器直接更改 |
| `model_runs`（或等效观测事件） | task ID、模型供应商/模型 ID、提示词版本、用量、耗时、状态、错误码 | 不默认存原文或完整响应；设置保留期与访问控制；不含 API Key |

### 8.1 关键约束

- 不采用全表无差别 CRUD 授权。
- `documents`、`document_chunks`、`health_metrics`、任务和资产关系按实际访问路径设计 RLS/服务端过滤。
- 所有用户可见数据查询都先做授权过滤，再做语义排序。
- 唯一索引只能保障索引条件定义范围内的唯一性；业务状态一致性还需要事务和状态检查。
- 若授权范围暂以逗号分隔字符串注入 PostgreSQL 上下文，内部 `space_id` 必须采用严格白名单格式并禁止逗号；更稳妥的实现是统一封装结构化编码/解码函数，不在业务代码中手工拼接任意标识。
- 删除空间前必须检查文档、资产引用、任务、版本系列、派生关系、成员和审计保留规则。
- 向量维度与 embedding 模型版本应由配置管理；模型变更时支持并存索引或可控全量重建。

### 8.2 版本更新事务伪流程

```text
BEGIN
  校验请求权限与 expected_current_doc_id
  SELECT document_series ... FOR UPDATE
  若 current_doc_id != expected_current_doc_id：返回 VERSION_CONFLICT
  创建新 documents 版本（先处于不可检索的待发布状态）
  写入版本关系和 Outbox 事件
  更新 document_series.current_doc_id
  标记旧版本为 SUPERSEDED，新版本保持 PENDING_PUBLISH
COMMIT

执行文件发布与索引构建
在完整性校验通过后，将新版本改为可检索状态
若发布失败：由恢复 Worker 重试或执行补偿；不假装跨系统事务已回滚
```

实施阶段应进一步验证：当前指针更新、文件可用状态和检索索引切换之间，是否存在短暂不可见窗口，以及系统如何向用户解释该状态。

## 9. MCP 接口与交互契约

### 9.1 工具边界

| 工具 | 用途 | 关键输入 | 安全与结果规则 |
|---|---|---|---|
| `search_knowledge` | 检索知识 | `query`、可选空间/类别/代码符号筛选 | 筛选值必须与授权范围取交集；返回版本和来源位置，不返回未授权结果 |
| `get_document_asset` | 获取原件/附件/完整 Wiki | `doc_id`、受控 `asset_type` | 不接受裸路径；每次请求重新授权；拒绝信息不得泄露文档存在性 |
| `ingest_document_or_file` | 文件或图片入库 | 内容/受控文件引用、目标空间或 AUTO、用户说明、幂等键（可选） | 目标越权直接拒绝；返回任务 ID 和状态，不虚报已提交 |
| `commit_memory_note` | 沉淀对话中的事实/结论 | 标题、摘要内容、目标、存储模式 | 对高风险或多意图内容要求确认；不重复追加同一事件 |
| `get_ingestion_task` | 查询任务状态 | `task_id` | 验证调用者是否有权读取该任务；返回阶段、错误与下一步操作 |
| `review_and_fix_knowledge` | 批准、重分类、修指标、回滚或晋升 | 动作、目标 ID、变更内容、预期版本 | 使用白名单动作和 schema 校验；按执行时权限再次校验；返回变更前后摘要 |
| `query_health_trends` | 查询健康指标趋势 | 人员、指标、日期范围 | 仅 Phase 2；必须校验家庭空间成员和健康类别授权；明确未复核数据 |

### 9.2 标准入库回执

```markdown
## 知识任务回执
- 任务 ID：<task_id>
- 状态：<COMMITTED / NEEDS_REVIEW / FAILED_RETRYABLE / FAILED_FINAL>
- 目标空间：<空间名或“待确认”>
- 文档：<标题或“尚未生成”>
- 原始资产：<受控引用；仅授权用户可打开>
- 来源：<页码/章节/表格等可用位置>
- 处理摘要：<短摘要>
- 需要复核：<无 / 具体字段和原因>
- 下一步：<检索 / 批准 / 重分类 / 重试 / 取消>
```

要求：

- `COMMITTED` 只能在真实提交完成后返回。
- `NEEDS_REVIEW` 必须显示待确认原因和可执行操作。
- `FAILED_RETRYABLE` 应说明系统会自动重试还是需要用户手动操作。
- 不在对无权用户的回执中暴露敏感标题、空间名或原件链接。
- MCP 协议负责工具输入输出，不保证所有客户端都能渲染自定义交互卡片；标准文本/结构化内容是基础，富 UI 是客户端适配能力。

### 9.3 网关事务上下文实现要求

Python 侧如需将连接、事务和授权上下文封装为 `async with`，必须实现真正的异步上下文管理器，例如使用 `contextlib.asynccontextmanager`，不能仅在普通 `async def` 中写 `yield` 就假设它可直接用于 `async with`。

伪代码轮廓：

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def profiled_transaction(pool, resolved_scope):
    async with pool.acquire() as conn:
        async with conn.transaction():
            # 使用事务级设置，默认先清空；scope 必须由可信授权逻辑生成。
            await conn.execute(
                "SELECT set_config('app.allowed_read_spaces', '', true), "
                "set_config('app.allowed_write_spaces', '', true)"
            )
            await conn.execute(
                "SELECT set_config('app.allowed_read_spaces', $1, true)",
                ",".join(resolved_scope.read_spaces)
            )
            await conn.execute(
                "SELECT set_config('app.allowed_write_spaces', $1, true)",
                ",".join(resolved_scope.write_spaces)
            )
            yield conn
```

这只是资源管理和事务上下文的示意。生产实现还需处理 Token 验证、类别范围、请求取消、超时、异常、审计、scope 编码约束和连接池复用测试；不得把未经验证的客户端输入直接塞入 `resolved_scope`。授权上下文的可信度来自受控服务端路径和数据库访问边界，而不是来自 `set_config` 这个函数本身。

### 9.4 审核与纠错操作

`review_and_fix_knowledge` 的动作必须是受控枚举，而不是任意数据库字段更新。建议支持：

- `APPROVE_REVIEW`
- `RECLASSIFY`
- `SPLIT_DOCUMENT`
- `FIX_EXTRACTED_FIELD`
- `REVERT_VERSION`
- `PROMOTE_COPY`
- `CANCEL_TASK`

每个动作都有独立输入 schema、权限规则、预期状态和失败返回码。涉及跨空间操作的 `PROMOTE_COPY` 必须展示源/目标空间、复制内容、敏感信息检查结果和目标可见成员，并要求显式确认。

## 10. Obsidian 控制台与双向同步

### 10.1 控制台视图

每个空间可提供 `_dashboard_控制台.md`，展示以下视图：

1. 待人工确认任务及候选理由。
2. 失败与可重试任务。
3. 当前版本与最近版本替代/补充记录。
4. 最近的人工修改、同步冲突和审核动作。
5. 最近备份、最近恢复演练和索引健康状态。
6. 空间文档数量、当前版本数、待处理任务与索引状态。

控制台是状态投影和管理入口，不是独立的权限事实源。Dataview 等插件适用于本地展示，但应验证插件访问权限、移动设备同步与跨设备冲突行为。控制台不得依靠显示隐藏字段实现访问控制。

### 10.2 文件监听器规则

- 只监听允许的 `wiki/` 路径和明确的文件扩展名；忽略暂存目录、Git 内部目录和临时文件。
- 每个文档记录 `content_revision` 与上次同步哈希。
- 只在差异确实属于正文或允许编辑的字段时触发同步。
- 系统字段发生异常变化时，拒绝更新权威数据库字段，并生成审核任务。
- 由同步服务自己写回的文件应携带操作 ID 或版本记录，避免触发无穷循环。
- 发生并发修改时使用乐观锁；不能可靠合并的情况下生成冲突副本，绝不静默覆盖任一方。
- 索引更新使用 Outbox 或可重放任务，避免正文已更新而向量索引永久滞后。

## 11. 健康档案专项（Phase 2）

### 11.1 数据处理流程

```text
原始报告归档
  -> 文档解析 / OCR / VLM 提取
  -> 保留原始识别文本与来源位置
  -> 指标 schema 校验（名称、数值、单位、日期、参考范围）
  -> 存疑指标 NEEDS_CHECK
  -> 用户/授权家庭成员人工核验
  -> 标记 HUMAN_VERIFIED 并记录核验历史
  -> 趋势查询与可追溯展示
```

### 11.2 健康数据约束

- 每个结构化指标必须关联 `source_doc_id` 和可用的源位置。
- 记录原始提取值、规范化值、单位、报告参考范围、测量日期、核验状态和修正历史。
- 参考范围优先采用原报告提供的区间；不得仅靠通用阈值推断医学结论。
- 置信度或图像可读性只能用于触发复核，不能当作医学正确性的证明。
- 报告模糊、单位缺失、日期不确定、姓名不确定或单位换算不明确时必须标记复核。
- 未经人工核验的指标展示时应标注“AI 提取，尚未核验”。
- 删除或更正健康指标时保留审计和来源链；避免在普通日志中输出健康数据详情。

## 12. 可观测性、备份与恢复

### 12.1 基础监控

至少监控：

- 入库成功率、失败率、待确认积压量、任务平均处理时间和重试次数。
- Worker 租约超时、死信/永久失败任务和 Outbox 积压。
- 文件与数据库状态不一致数量、索引落后时间、损坏/缺失文件数量。
- 令牌撤销传播时延、越权拒绝次数和可疑文件访问尝试。
- 数据库连接池耗尽、慢查询、索引体积和 embedding 失败率。
- 备份成功时间、备份可读性与最近一次恢复演练结果。

### 12.2 备份策略

- 对 PostgreSQL 业务数据、Vault 原始文件、Wiki 文件和配置分别制定备份策略。
- Git 历史只能覆盖已纳入仓库且未被清理的文件，不替代数据库备份或独立加密备份。
- 备份凭证与生产读写凭证分离；加密密钥不可只存在于被备份的同一环境中。
- 明确 RPO、RTO、保留期限、异地副本和恢复访问控制。
- 定期演练“从备份恢复”与“索引重建”，两者分别验收。

### 12.3 恢复目标

MVP 不直接承诺“15 分钟内无损重建一切”。建议先在指定数据规模下测量，并分别定义：

- **数据库恢复：** 从数据库备份恢复用户、授权、文档元数据、任务、版本指针和审计。
- **文件恢复：** 恢复原始资产与 Wiki 正文，并验证 SHA-256。
- **索引重建：** 从有效正文和元数据重建全文/向量索引。
- **一致性核对：** 比较数据库文档、正式文件、版本指针和索引覆盖率，输出差异报告。

只有经过至少一次完整演练后，才可以把测得的时间写入正式 SLO。

### 14.5 恢复与运营

- 备份恢复、文件恢复、索引重建必须分开测试和报告。
- 数据库恢复后应能校验文档系列、当前版本指针、授权关系和任务审计的完整性。
- 索引重建后应通过固定问题集和文档数量/哈希对账验证。
- RPO/RTO 在完成真实演练后确认；在此之前不把 15 分钟作为对外承诺。
- 高优先级安全告警、永久失败任务和同步冲突均须能被定位到具体任务 ID。

## 15. 风险、依赖与未决事项

### 15.1 主要风险登记表

| 风险 | 影响 | 缓解策略 | 责任阶段 |
|---|---|---|---|
| R-01：授权逻辑与 RLS 不一致 | 数据越权 | 授权矩阵、逐表策略、负向测试、最小权限账号 | Phase 0 |
| R-02：自定义 DB 上下文被不可信 SQL 修改 | RLS 保护边界被绕过 | 禁止客户端直连、参数化 SQL、受控查询层；必要时强化身份绑定 | Phase 0 |
| R-03：文件系统与 DB 部分提交 | 孤儿文件、幽灵记录、索引滞后 | Saga、Outbox、恢复 Worker、对账任务 | Phase 0/1 |
| R-04：Markdown 同步冲突 | 用户内容丢失或索引过期 | 内容修订号、乐观锁、冲突副本、可重放同步 | Phase 1 |
| R-05：版本误替代 | 新旧知识错误切换 | 显示 Diff、明确确认、系列锁、可审计回滚 | Phase 1 |
| R-06：AI 路由误判 | 错误归档或敏感信息暴露 | 授权优先、敏感预检、待确认机制、测试集 | Phase 1–3 |
| R-07：外部组件升级或许可证变化 | 运行中断或替换成本 | 固定版本、记录许可证、接口封装、退出路径 | 全阶段 |
| R-08：健康指标识别错误 | 用户误读健康信息 | 原始证据、复核状态、规则来源、纠错历史 | Phase 2 |
| R-09：备份包含敏感资料 | 隐私泄露 | 加密、独立凭证、访问控制、保留和删除规则 | Phase 1–2 |
| R-10：工作量超出估算 | 交付延期、质量下降 | 以 Exit Criteria 管理里程碑，先跑通最小闭环 | 全阶段 |
| R-11：模型 ID、能力或区域不可用 | 入库/检索不可用或需要临时改造 | 配置化模型 ID；Phase 0 验证目标地域 API；保持供应商适配层可替换 | Phase 0/1 |
| R-12：外部模型数据处理边界不清 | 敏感数据外发或合规风险 | 按空间/类别设外发策略；健康与机密资料先审批；默认最小化发送内容 | Phase 0–2 |

### 15.2 Phase 0 需要验证的技术选型

- PostgreSQL 的实际版本、`pgvector`、`ltree` 与全文检索能力是否匹配部署环境。
- 首期 Chat/Vision 与 Embedding 模型在目标地域的实际可用性、维度、成本、数据传输范围、限流和升级重建策略。
- Model Adapter 的统一接口、请求 schema、有限重试、调用计量与敏感内容日志策略。
- n8n 在复杂状态机、租约、并发、重试和补偿上的实际能力；必要时将核心状态机抽离至 Python Worker。
- 文档解析方案对 PDF、扫描件、表格、图片和中文内容的准确率、资源消耗及许可证限制。
- Obsidian 插件行为、文件监听可靠性、多设备同步和冲突处理。
- 本地文件系统、Docker Volume 或 NAS 存储对原子重命名、权限、符号链接和备份的实际支持。
- FastMCP 与目标 MCP 客户端的工具调用、附件传递、返回结构和错误呈现能力。

### 15.3 未决产品规则（必须记录决策，不允许实现时自行猜测）

1. 同一原始文件在两个空间共享时，是复用资产字节还是复制物理文件；无论哪种都必须保持每个文档独立授权。
2. 用户是否可以在 MVP 中永久删除原件，还是仅支持归档/软删除。
3. 用户修改 `version_key` 时是创建新系列，还是通过专用迁移操作改变系列关系。
4. 家庭成员之间的权限是否支持按文档细分，还是先采用空间级角色。
5. 健康指标支持哪些人、指标类型和单位；是否需要导出与数据迁移。
6. Git 远程备份是否允许包含原件、健康档案或仅包含 Markdown；不同空间需单独确定策略。
7. 个人知识晋升至家庭/企业空间时，是否保留源文档、是否需要脱敏以及谁有审批权。

## 17. 最终产品决议

1. **保留统一底座，限制一期承诺。** Space 作为可扩展的数据抽象，但 MVP 只实现个人知识闭环。
2. **优先保证知识可信。** 原始证据、可追溯正文、版本关系、人工纠错和失败恢复先于更高比例的自动路由。
3. **权限必须由服务端强制执行。** LLM 仅提供建议；文件路径、类别、空间和版本都不可由模型输出直接决定授权。
4. **将“自动回滚”改为“可恢复和可补偿”。** 不宣称文件系统与 PostgreSQL 存在统一原子事务。
5. **将安全承诺转化为测试证据。** 对外宣称前，必须有相应的负向测试和恢复演练记录。
6. **阶段计划以验收条件为准。** 周期是估算，安全验证和真实恢复演练不能被工期压缩。

### 最终结论

ContextHub 的差异化价值在于将知识整理、版本演进、可追溯检索和权限治理统一为可验证的工作流。最终技术组合为：**FastMCP 作为受控工具入口，n8n/Python Worker 负责异步编排，PostgreSQL 负责权限元数据、任务、版本与检索索引，文件存储负责原始证据与 Markdown 正文，Model Adapter 统一接入外部模型。** 首期建议以 `qwen3.8-flash` 承担常规理解/编译/回答，以 `text-embedding-v4`（1024 维）承担语义检索向量生成；复杂任务可选用 `qwen3.8-max`，Reranker 暂不作为 MVP 必需项。上述模型须在目标地域与账户中通过 Phase 0 验证后启用。

最优产品路线不是一次完成个人、家庭与企业全部功能，而是先把个人知识的完整生命周期做好：**原件可追溯、写入可幂等、内容可纠错、版本可恢复、查询不越权；模型可替换、调用可审计、敏感数据有明确外发策略。** 当这一闭环经过真实故障和负向安全测试后，再逐步开放家庭健康与企业组织能力。
